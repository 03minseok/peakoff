# PEAKOFF

**예측 기반 혼잡 회피 여행 플래너.**

사용자가 직접 짠 여행 코스를 공공 관광 예측 데이터로 진단해, 붐빌 것으로 예측되는 장소를
한적한 대안지로 바꾸도록 돕는다. 유명 관광지 쏠림(오버투어리즘)을 **사후 통제가 아니라
계획 단계의 선택**으로 푼다.

> 2026 관광데이터 활용 공모전 ②-2 웹·앱 구현 부문 출품작 · 지정과제 2번(과밀화)

---

## 무엇을 하는 서비스인가

혼잡을 피하는 길은 둘뿐이다 — **날짜를 바꾸거나, 장소를 바꾸거나.** 이 서비스는 둘 다 제안한다.

```
코스를 짠다 → 날짜별·장소별 한적도를 진단한다 → 붐비는 자리를 찾는다
                                              ├─ 더 한적한 날짜를 제안
                                              └─ 근처의 한적한 대안지를 제안
                                                   ↓
                                   원안 vs 개선안 총점 비교 → 저장
```

경주를 모르는 사용자를 위해 **설문 2문항으로 코스 초안을 받는 입구**가 따로 있고,
로그인 없이 게스트로 전체 흐름을 쓸 수 있다. 로그인은 코스를 **저장하고 비교하기 위한**
선택지이지 진입 장벽이 아니다.

**대상 지역 7곳** — 경주 · 제주시 · 서귀포시 · 여수 · 속초 · 태안 · 춘천.
목록의 원천은 `SupportedRegion` 하나이고, 화면은 `GET /api/regions`로 받아 간다.
아무 데나 늘리지 않는다 — 세 조건(가장 적은 배지 20% 이상 · 집중률 예측 40곳 이상 ·
자치구로 안 쪼개진 단일 시군구)을 통과한 시군구만 들어간다(`analysis/national/RESULTS.md`).

## 점수는 둘뿐이다

셋째 점수를 만들지 않는다. 화면에 없는 값으로 목록을 줄 세우면 "왜 이게 1등인지"를
설명할 수 없기 때문이다.

| | 무엇 | 어디에 |
|---|---|---|
| **한적도** | 집중률 예측을 뒤집은 원본 지표. 그 장소가 그날 얼마나 덜 붐빌지 | 진단·대안·홈 어디서나 3단계 배지 |
| **추천도** | "이 서비스가 그곳을 대안으로 얼마나 미는가"라는 **관계값** | 장소 교체 추천에서만 |

- **추천도 = 0.7 × 한적도 + 0.3 × 동선 근접도.** 한적도의 비중이 가장 크다 —
  한적한 곳으로 사람을 보내는 것이 추천의 목적 자체다.
- **인기도를 가점으로 쓰지 않는다.** 인기 장소 = 붐비는 장소이므로 과제와 정면으로 모순된다.
  실측에서도 연관 순위와 한적도는 음의 상관이었다(6개 지역 26,819쌍, 켄달 타우 −0.073).
  연관 관광지 데이터는 점수가 아니라 **후보를 거르는 문**으로만 쓴다.
- **구성 내역을 화면에 편다.** 항목·점수·반영 비율·근거를 서버가 내려보내고 화면이 그대로
  그린다. 심사의 "추천도를 어떻게 산출하나요?"에 화면을 가리켜 답할 수 있어야 한다.
- **코스 총점은 슬롯 한적도의 평균**이다. 추천도가 섞이지 않아야 원안 대비 개선폭이 그대로 읽힌다.

### 추천 분산 — 이 저장소에서 가장 신경 쓴 장치

같은 대안이 모든 사용자에게 반복 추천되면 **그곳이 새로운 혼잡지가 된다.** 2차 오버투어리즘이다.
그래서 상위 후보 Pool을 만든 뒤 점수에 비례한 **가중 무작위**로 뽑는다.

```
거르기(지역·분류·좌표·중복·한적도 하한) → 점수 계산 → 상위 Pool → 가중 무작위 → 세션에 저장
```

- **뽑은 뒤 점수순으로 다시 정렬하지 않는다.** 정렬로 덮으면 최고점이 언제나 1등이 되어
  이 장치가 아무 일도 하지 않게 된다(고정률 95~100% → 38~42%로 고친 이력이 있다).
- **캐시는 원자료 층에만 둔다.** 완성된 대안 목록을 캐시해 모두에게 돌려주면 분산이 통째로 죽는다.
- 화면을 다시 그릴 때마다 다시 뽑지 않는다 — 시트를 닫았다 열었을 뿐인데 목록이 바뀌면
  되돌아갈 후보를 찾지 못한다.

## 데이터

**공공데이터포털의 관광 OpenAPI를 매 요청 호출한다.** 파일(Excel·CSV) 내려받기나
DB 적재로 대체하지 않는다 — 인증키 호출 이력이 심사 대상이기 때문이다.
성능을 위한 **인메모리 캐시(TTL 6시간)** 만 둔다. 원본이 1일 1회 갱신되므로 그 이상은 의미가 없다.

| 데이터 | 역할 | 경로 (`https://apis.data.go.kr/B551011/…`) |
|---|---|---|
| 국문 관광정보 | 지역 카탈로그·검색·장소 상세 | `KorService2/areaBasedList2` · `detailCommon2` |
| 관광지 집중률 방문자 추이 예측 | **한적도의 원천** | `TatsCnctrRateService/tatsCnctrRatedList` |
| 관광지별 연관 관광지 (티맵 기반) | 대안 후보 생성 | `TarRlteTarService1/areaBasedList1` |
| 중심 관광지 | 검색 전 대표 관광지 칩 · 코스 초안의 첫 장소 | `LocgoHubTarService1/areaBasedList1` |
| Kakao 지도 SDK | 지도 표시 **전용** (좌표는 보완하지 않는다) | — |

> **활용신청은 API마다 따로 한다.** 포털 계정이 아니라 API 단위로 키가 등록되고,
> 승인 표시가 뜬 뒤에도 게이트웨이 반영에 1~2시간 걸린다.

알아 둘 제약:

- 이 데이터는 실시간이 아니라 **예측·통계값**이다. UI 문구도 "실시간 혼잡"이 아니라
  **"예상 혼잡"** 으로 쓴다.
- 집중률 예측은 **조회 시점부터 24~30일**이고 과거는 없다. 길이가 고정이 아니라서
  숫자를 코드에 박지 않고 응답의 마지막 날을 읽어 내려준다. 창 밖 날짜도 **막지 않는다** —
  여행은 원래 미리 계획한다.
- 집중률 응답에는 콘텐츠 ID가 없고 **관광지 이름 문자열뿐**이라, 국문 관광정보와는
  이름 매칭으로 잇는다. 후보가 여럿이면 자동 확정하지 않는다 — 잘못 이으면 다른 장소의
  혼잡도를 그 장소의 것이라고 말하게 된다.
- **화면 문구에는 특정 기관명·로고를 쓰지 않는다.** 출처는 "공공데이터 기반"으로 적는다.
- 사용자 GPS를 서버로 보내지 않는다. 지역·장소는 사용자가 직접 고른다.

## 기술 스택

| | |
|---|---|
| 백엔드 | Java 21 · Spring Boot 4.1 · Spring Security + JWT(jjwt) · JPA · H2(개발) / PostgreSQL(배포) |
| 프론트 | React 19 · TypeScript · Vite · Tailwind CSS v4 · React Router · Kakao Maps SDK |
| 분석 | Python (검증용 노트북·스크립트) |
| CI/CD | GitHub Actions · GHCR · Docker Compose(EC2) · Vercel |

DB에는 **회원·저장 코스·찜만** 담는다. 관광 데이터는 적재하지 않는다.
파이썬은 **검증용 연구실**이고 서비스에 붙지 않는다 — 확정된 규칙(임계값·점수식·가중치)만
자바로 이식한다. 별도 파이썬 API 서버를 띄우지 않는다.

## 로컬에서 돌리기

**인증키 없이도 뜬다.** 기본값이 목업이라 `clone → 실행`만으로 전체 흐름을 볼 수 있다.

```bash
# 1) 백엔드 — http://localhost:8080 (API 문서: /docs)
cd backend
./gradlew bootRun

# 2) 프론트 — http://localhost:5173
cd frontend
npm ci
npm run dev
```

Vite 개발 서버가 `/api`를 8080으로 대신 전달하므로 CORS 설정이 필요 없다.
포트를 바꾸면 `vite.config.ts`와 `application.yaml` **양쪽**을 고쳐야 한다.

### 실제 데이터로 돌리려면

인증키와 데이터 소스 스위치를 넣는다. 로컬에서는
`backend/src/main/resources/application-local.yml`(gitignore 대상)에 적고,
배포에서는 같은 이름의 **환경변수**로 넣는다. **키를 코드나 커밋에 두지 않는다.**

| 환경변수 | 무엇 | 없으면 |
|---|---|---|
| `KTO_SERVICE_KEY` | 공공데이터포털 **일반 인증키(Encoding)** | 실연동 호출이 전부 실패 |
| `KTO_CONGESTION` | 한적도 소스 `mock` \| `real` | `mock` |
| `KTO_PLACE` | 장소 소스 `mock` \| `real` | `mock` |
| `KTO_RECOMMENDATION` | 대안 추천 소스 `mock` \| `real` | `mock` |
| `PEAKOFF_JWT_SECRET` | 토큰 서명 키 | 임의 키로 떠서 재시작마다 로그인이 풀린다 |
| `KAKAO_CLIENT_ID` / `_SECRET` / `_REDIRECT_URI` | 카카오 로그인 (REST API 키) | 소셜 로그인만 비활성 |
| `NAVER_CLIENT_ID` / `_SECRET` / `_REDIRECT_URI` | 네이버 로그인 | 소셜 로그인만 비활성 |
| `PEAKOFF_DEV_ENDPOINTS` | `/api/dev/**` 개방 (호출량 확인 화면) | `false` |
| `SPRING_DATASOURCE_URL` / `_USERNAME` / `_PASSWORD` | 배포용 PostgreSQL | 파일 H2(`backend/data/`) |
| `VITE_KAKAO_MAP_KEY` | Kakao 지도 **JavaScript 키** (`frontend/.env`) | 지도 자리에 안내가 뜨고 목록 편집은 그대로 된다 |

> ⚠️ `KTO_SERVICE_KEY`는 이미 URL 인코딩된 값이라 그대로 실어 보낸다. 코드에서 한 번 더
> 인코딩하면 `%2B`가 `%252B`가 되어 다른 키로 읽히고 거절당한다 — 가장 흔히 터지는 자리다.
>
> ⚠️ `KTO_PLACE=real`로 바꾸면 장소 ID가 `mock-bulguksa`에서 콘텐츠 ID(`126166`)로 바뀐다.
> 목업으로 저장해 둔 코스의 옛 ID는 더 이상 찾을 수 없다.
>
> ⚠️ `KTO_RECOMMENDATION`은 `KTO_PLACE`와 짝이다. 장소가 목업인데 추천만 `real`이면
> 후보를 카탈로그로 되돌리지 못해 빈 목록이 나온다.

## 확인하기

```bash
cd backend  && ./gradlew build          # 컴파일 + 테스트
cd frontend && npx tsc --noEmit         # 타입
cd frontend && npm run lint             # oxlint
cd frontend && npm run build            # 빌드
```

**테스트는 요청할 때만 쓴다** — 다만 점수 계산과 도메인 검증은 예외로 단위 테스트를 둔다.
숫자를 바꿔도 아무도 알려주지 않으면 그 숫자가 근거를 잃기 때문이다.

화면은 **실제 브라우저로 열어 본다.** 코드만 읽어서는 안 보이는 것들(가로 스크롤, 콘솔의
붉은 줄, 모바일 브라우저 도구막대와의 자리 다툼)을 잡는 자리다. 390px과 1280px 두 폭으로 찍는다.

```bash
# 터미널 셋이 필요하다: 백엔드 · 프론트 · 아래 명령
cd frontend && npm run ui:shot          # 결과: npm run ui:report
```

> 이 묶음은 CI에서 돌리지 않는다. 브라우저를 받는 데만 수백 MB가 들고, 실제 데이터에
> 기대는 화면이라 외부 API 상태에 따라 결과가 흔들린다. PR을 붉게 만드는 원인이 우리
> 코드 밖에 생기면 검사 자체를 믿지 않게 된다.

**마지막 확인은 실물 폰이다.** 크로미움 에뮬레이션으로 재현되지 않는 것이 있다 —
`overscroll-x-contain`을 믿고 만든 캐러셀이 실물 아이폰에서 페이지째 밀린 이력이 있다.

## 배포

| | 어디 | 어떻게 |
|---|---|---|
| 프론트 | Vercel | `frontend/vercel.json`이 `/api/*`를 백엔드로 rewrite. SPA fallback 포함 |
| 백엔드 | EC2 | `main` push → 이미지 빌드 → GHCR → 서버에서 `docker compose up -d` |
| DB | 같은 EC2의 PostgreSQL 컨테이너 | 포트를 밖으로 열지 않는다. 볼륨으로 데이터 보존 |

- **CI(`ci.yml`)와 배포(`deploy.yml`)를 나눠 두었다.** 한 파일에 두면 "PR일 땐 배포하지 마라"
  같은 조건문이 늘고, 그 조건이 틀리면 배포가 조용히 안 나간다.
- CI에는 `application-local.yml`이 없으므로 목업으로 돈다 — 인증키 없이 검사되고
  일일 한도를 태우지 않는다.
- 이미지 태그에 커밋 SHA가 붙는다. 지금 도는 것이 어느 커밋인지 서버에서 바로 알 수 있고
  되돌리기도 태그만 바꾸면 된다.
- 배포에 쓰는 `.env`(인증키·DB 비밀번호·JWT 시크릿)는 저장소에 없다. GitHub Secrets에 두고
  배포할 때 서버로 올린다.
